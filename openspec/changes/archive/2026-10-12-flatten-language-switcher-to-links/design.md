# Design

## Context

语言切换目前是导航栏里唯一依赖 JavaScript 才能使用的偏好控件。三个语言项本身是直出链接，但被 `<details class="nav-preference-control language-control">` 包着，`siteNavScript` 用 `focusout` + `queueMicrotask` 在失焦时关闭它。这段关闭逻辑与点击手势在同一事件循环内竞争，结果见 `proposal.md`。

对照物是同一容器里的主题切换：三个裸按钮、无开合外壳、零 JS，实测工作正常。两者结构上的唯一差别就是那层壳。

实测基线（headless Chrome 154，线上 `colors-cc.top`，桌面 1280×900）：

| 观察项 | 结果 |
|---|---|
| `/en`、`/zh`、`/ja` 上点击语言项 | 只有 `pointerdown`/`mousedown`，无 `mouseup`、无 `click`、无导航 |
| 点击 `summary` 展开面板 | 正常展开（失败点在选项，不在开关） |
| 三页主题按钮点击 | 正常生效（证明注入点击的方法本身可靠） |
| 展开面板后按一次 `Tab` | 面板关闭、焦点落到 `BODY`、选项不可见，键盘到不了链接 |
| 桌面展平后点击 `简体中文` | 成功导航到 `/zh`，`<html lang="zh-CN">` |
| 桌面展平后 header 宽度 | 工具区 231px → 288px，导航面板可用 1075px，零溢出 |

移动端基线（把 `<details>` 去掉后逐宽度实测，菜单展开状态）：面板宽度 360/390/430/760px 视口下分别为 332/362/402/732px。三个语言自称的自然宽度为 `English` 63px、`简体中文` 67px、`日本語` 55px。

## Goals / Non-Goals

**Goals:**

- 语言切换在无 JavaScript 的情况下即可完成：链接服务端直出、常显、可直接点击、可 Tab 到达、可用键盘激活。
- 删除唯一需要 JS 维护的开合状态，使鼠标与键盘两条路径共享同一个不会失败的机制。
- 语言入口进入每一页的初始渲染 DOM，不再藏于收合界面之后。

**Non-Goals:**

- 不改 URL 方案、canonical、hreflang、sitemap 或路由。
- 不改 `src/client/runtime.ts` 中"切换语言保留查询条件与片段"的行为。
- 不改文案、语言集合或部署差异（CN 站仍只提供简体中文，`enabledLocales.length === 1` 时不渲染语言控件）。
- 不重构主题切换、导航菜单或其它偏好控件。

## Decisions

### 决策 1：删除开合外壳，语言切换改为常显分段控件

语言控件变成与主题控件同构的 `.nav-preference-control` + `.nav-segmented`：容器保留 `role="group"` 与 `aria-label`，内部三个直出 `<a>`，当前语言用 `aria-current="page"` 标记。

- 理由：主题切换已验证在同样位置、同样尺寸下工作正常，两者同构后语言切换继承其可靠性；开合状态、失焦关闭、Escape 处理、`toggle` 标签维护一并消失。
- 已否决：**保留下拉但改用 document 级 pointerdown 判定关闭**。能修好鼠标路径，但键盘路径仍需单独设计焦点管理——等于继续维护一层只为装饰存在的状态机，与本变更的目标相反。
- 已否决：**保留下拉、只把 `queueMicrotask` 换成宏任务延迟**。实测延迟 250ms 仍然失败（面板照样在选择前关闭），而且把正确性押在一个时间常数上。

### 决策 2：当前语言的标示从 `summary` 挪到链接上的 `aria-current`

原先"English"显示在 `summary` 上，兼作当前语言提示。展平后改由 `.language-option[aria-current='page']` 承担，该规则已存在（青色高亮），视觉提示不变。三个语言自称同时常显，访客不再需要先展开才知道有哪些语言可用。

### 决策 3：移动端用整行承载，三个语言各自占满宽度

760px 断点以下，`.nav-actions` 已是纵向网格，语言行改为占满一行的三段式；语言项放弃通用的固定 44×44，改为按标签自然宽度伸展，主题按钮保持 44×44 方块。

- 宽度账（390px 视口，内容宽 362px）：三个标签连同左右 10px 内边距共约 195px，容纳于 362px，无截断，实际呈现为三等分（实测 121/124/113px）。
- 已知约束：该断点下既有的 `.nav-switch-option { width: 44px; ... }` 与基础规则同特异性、靠源码顺序胜出，因此移动端的覆盖规则必须提高特异性，作用域限定在语言控件内，避免连带拉伸主题按钮。设计阶段以高特异性规则验证可行（选项伸展至 121/124/113px，主题按钮仍为 44×44）。
- 已否决：**移动端沿用固定 44×44**。`English`/`简体中文` 会溢出（`scrollWidth` 45px 对 44px），标签被裁切，且"English"这种宽标签在 0.72rem 字号下必然显示不全。
- 已否决：**移动端换成 `EN / 中文 / 日本語` 缩写**。需要为三种语言新增短标签文案与 i18n 键，而实测全称本来就放得下。

### 决策 4：删除而非重写 `siteNavScript` 中的语言部分

该脚本剩下的职责只有导航菜单的移动端开合与标签维护，属于另一个控件。语言相关的 `focusout`、`queueMicrotask`、Escape 三处监听整体移除，不保留"以防万一"的兜底——保留任何关闭副作用都会重新引入打断手势的可能。

## Risks / Trade-offs

- **[新增及既有断言大量依赖被删标记]** → 任务中单列一步：先跑全量测试列出所有引用 `.language-toggle`、`language-control`、`>简体中文</a>` 的断言，逐条改为对展平结构的断言，避免"测试改到哪算哪"。
- **[仅按需渲染，且只在 Chromium 内核验证过]** → 本设计不依赖任何浏览器私有行为，只用标准 `<a>` 与 CSS；但仍把"鼠标点击 + 键盘激活"作为可执行回归覆盖写进任务，在闸门层面保证而不是靠人工确认。
- **[归档会被拒绝]** → `openspec validate` 已确认：本变更的两份 delta 都是 MODIFIED，而 `openspec/specs/` 下尚不存在 `japanese-localization` 与 `visitor-tool-workflows` 这两个能力（它们目前只存在于未归档的 `add-japanese-localization-and-tool-ux` 的 delta 中），归档会以 "target spec does not exist" 拒绝。缓解：先归档该前置变更，再归档本变更；顺序颠倒时归档会**显式失败**而非静默丢失需求的修改内容，因此不要用 `openspec sync` 绕过。
- **[移动端规则与既有 44px 规则特异性相同即失效]** → 覆盖规则必须带作用域前缀，且在 760px 断点内实测通过后才算完成；把它列为任务中的验证项，而非写完即认为生效。
- **[展平后 header 更宽，长文案语言可能挤压布局]** → 当前三种语言自称的自然宽度已实测（最宽 67px），桌面端总增量 57px、导航面板余量充足；若将来加入更长的语言名，移动端整行方案仍能容纳，桌面端需要重新量一次。

## Migration Plan

1. 删除 `nav-controls.ts` 中的开合外壳，语言控件改为常显分段结构。
2. 删除 `site-chrome.ts` 中 `.language-control` 的 `focusout`、`queueMicrotask`、Escape 监听。
3. 清理 `styles.ts` 中下拉定位与 `:not([open])` 隐藏规则，新增移动端整行规则。
4. 更新依赖旧标记的断言，并补上鼠标点击与键盘激活的行为覆盖。
5. 桌面与 760px 以下逐个宽度实测确认无溢出、无截断、语言与主题按钮各自形态正确。

回滚：本变更只涉及服务端渲染的标记、CSS 与一段脚本，回滚即还原这三个文件；无数据迁移、无路由变更、无外部依赖变化。
